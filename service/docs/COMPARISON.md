# Two-version comparison

`POST /scans/compare` (and `app/comparison/`) compares an older and a newer
version of a table. It is deterministic and statistical only: no LLM is called
and no row data leaves the process. It stores nothing.

`COMPARISON_VERSION: 0.1.0` (`app/version.py`).

## What it reports

| Area | What | Notes |
|---|---|---|
| Schema | columns added / removed, probable renames, inferred-type changes, column-order change | A rename is *proposed* when two columns agree on at least 95% of matched rows (or, with no key, share 95% of distinct values), with at least 20 rows of support. It is not certain. |
| Rows | unchanged / modified / added / removed, and which columns changed | Matched by a key column, never by position. The key is auto-detected from an id-style column that is unique and non-blank in both files, or passed as `key_column`. |
| Volume | row-count change in percent | Flagged at 10% by default. A heuristic, not a forecast. |
| Nulls | blank-rate change per shared column | Flagged at 5 percentage points by default. |
| Drift | PSI per shared column | Categorical: category shares. Numeric: 10 quantile bins cut from the older version. Identifier columns, free text and high-cardinality columns are reported as *not evaluated*, with the reason. |
| Integrity | order-independent, format-normalized content hash of the shared columns | A mismatch proves content differs. It does not say who changed it or why. |

## Normalization

Cells are trimmed. Anything that parses as a finite number is compared by exact
decimal value, so `$12,345.00` equals `12345`; a reformat shows up as a type
change, not as thousands of modified rows. Leading-zero values such as zip codes
stay text. `nan` and `inf` are text. Everything else compares exactly.

## Thresholds

PSI bands default to 0.10 (warning) and 0.20 (critical), configurable per call
or with `PSI_WARN_THRESHOLD` / `PSI_CRITICAL_THRESHOLD`. Published sources
disagree on the upper edge; these are heuristics, not universal truth. PSI also
depends on binning, so compare bands, not exact digits.

**Outlier policy.** PSI is computed on every value, extreme values included.
Nothing is trimmed or winsorized, so the numbers are reproducible from the files
alone. The consequence is visible: on the sample `amount` column the reference
file's PSI excluded the injected `99999999` values and reads 0.1465, while this
implementation includes them and reads about 0.143. Both land in the same band.
Compare bands, not digits.

**Format change vs type change.** When a column's inferred type moves between
integer and float and, with rows matched by key, none of its values differ after
normalization (`12345` vs `$12,345.00`), it is reported as a *format change,
values unchanged* (`column_format_changed`), not as a type change. Without a key
the claim cannot be checked, so it stays a type change. If any value differs it
also stays a type change.

## Without a key

If no usable key exists, rows are compared by normalized content: added and
removed rows can be counted, but *modified* rows cannot be identified, and the
response says so in `warnings`.

## Validation

`eval/datasets/versions/` holds three forged versions of one table with known,
planted changes and `versions_truth.json` (generated by `gen_versions.py`). The
data is synthetic; the comparisons of it are real. `tests/test_comparison.py`
asserts the comparison reproduces the truth file: the 890 / 60 / 250 / 50 row
summary, every added, removed and modified id with its changed fields, the PSI
bands, the `phone` to `phone_number` rename, and zero value changes when only
the formatting changed.

## Privacy

The profiles in the response hold counts, rates and numeric aggregates. Frequent
values are withheld for any column that looks personal (email, phone, name,
address, and similar) or has more than 20 distinct values. Modified-row detail
in the response does include the old and new cell values for the rows that
changed, returned to the caller who uploaded them; it is not stored.
